# Design: Add TypeScript, C#, PHP, and Swift to relinted

## Problem

relinted currently supports 6 C-family languages (C/C++, Perl, Rust, JavaScript, Go, Java). Users want support for TypeScript, C#, PHP, and Swift.

## Goals

- Add TypeScript, C#, PHP, and Swift to relinted
- TypeScript and C# reuse existing tokenizers (no new files)
- PHP and Swift get new `internal/php/` and `internal/swift/` packages
- Each language gets example files and tests
- Follow existing patterns: 4 files per new language package

## Non-Goals

- Full semantic parsing of PHP or Swift (opaque tokens only)
- Support for additional languages beyond these four

## Approach

### TypeScript (.ts)

Reuse JavaScript tokenizer and punctuation extractor. Add `.ts` extension mapping to `extToLang` in `main.go`. Import `js` package if not already imported.

Changes: 1 file (`cmd/relinted/main.go`), 2 lines added to `extToLang` map, 1 import added if needed.

### C# (.cs)

Reuse Java tokenizer and punctuation extractor. Add `.cs` extension mapping to `extToLang` in `main.go`. Import `java` package if not already imported.

Changes: 1 file (`cmd/relinted/main.go`), 2 lines added to `extToLang` map, 1 import added if needed.

### PHP (.php)

New `internal/php/` package with 4 files:

- **tokenize.go**: Language-specific tokenizer. Handles heredocs (`<<<'ID'\n...\nID;`) and double-quoted strings with interpolation (`"Hello $name"`) as opaque string tokens. Single-quoted strings, standard C-style comments (`//`, `/* */`), and PHP tags (`<?php`, `<?`, `?>`) as separate tokens.
- **punctuation.go**: Identifies `{`, `}`, `;` as punctuation marks to relocate. Same pattern as other languages.
- **format.go**: Identical 8-step pipeline (same as all other languages).
- **format_test.go**: Tests against ground truth file.

### Swift (.swift)

New `internal/swift/` package with 4 files:

- **tokenize.go**: Language-specific tokenizer. Handles optional chaining (`?`) after identifiers as opaque token, nil coalescing (`??`) as opaque token, `@` attributes as opaque tokens, string interpolation (`\(...)`) as opaque sub-token. Standard C-style comments and braces as usual.
- **punctuation.go**: Identifies `{`, `}`, `;` as punctuation marks to relocate. Same pattern as other languages.
- **format.go**: Identical 8-step pipeline (same as all other languages).
- **format_test.go**: Tests against ground truth file.

### Example Files

Each language gets two example files:
- `examples/linted-example-N.<ext>` — source input
- `examples/relinted-example-N.<ext>` — expected output (generated by running relinted)

Numbering: TypeScript=9, C#=10, PHP=11, Swift=12.

### Documentation Updates

- `README.md`: Add to banner, detection table, usage examples, before/after example, example file table, notes section
- `Justfile`: Add `test-php` and `test-swift` targets
- `cmd/relinted/main.go`: Update help text and supported languages list

## File Structure

```
internal/php/
  tokenize.go
  punctuation.go
  format.go
  format_test.go

internal/swift/
  tokenize.go
  punctuation.go
  format.go
  format_test.go

examples/
  linted-example-9.ts
  relinted-example-9.ts
  linted-example-10.cs
  relinted-example-10.cs
  linted-example-11.php
  relinted-example-11.php
  linted-example-12.swift
  relinted-example-12.swift
```

## Implementation Order

1. TypeScript (trivial, reuses JS)
2. C# (trivial, reuses Java)
3. PHP (new tokenizer, heredocs + interpolation)
4. Swift (new tokenizer, optionals + closures)

## Trade-offs

- **Opaque tokens for PHP heredocs and Swift string interpolation**: Simplifies tokenizer significantly. We don't parse nested expressions inside strings. Acceptable because relinted only needs to format braces/semicolons — string content doesn't affect formatting.
- **PHP tags as tokens (not punctuation)**: `<?php` and `?>` are not relocated. They stay in place. This is correct behavior — they're language delimiters, not structural punctuation.
- **Swift optional `?` as opaque token**: We don't try to distinguish between optional `?` and multiplication `*` in all cases. The heuristic: `?` after an identifier or closing brace is optional; `?` in other positions could be ambiguous but rare in practice.
